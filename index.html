A borough gap that mostly didn't survive checking against the complete data

A 50,000-row sample suggested Bronx and Queens restaurants had significantly worse odds of a B or C grade at re-inspection than Manhattan. Against the complete 295,048-row NYC DOHMH population, that gap shrinks by more than half and misses conventional significance — Queens sits right at the edge, Bronx doesn't clear it. The finding

A small, mostly-not-significant borough effect

A restaurant-clustered logistic regression on 14,414 linked initial → re-inspection visits (11,095 unique restaurants) from the complete NYC DOHMH extract finds that Bronx (OR 1.12, 95% CI 0.97–1.30, p=.110) and Queens (OR 1.11, 95% CI 1.00–1.23, p=.056) restaurants show a small tendency toward worse odds of a B/C grade at re-inspection than Manhattan, adjusted for prior score, cuisine, and year — but neither clears conventional significance. Brooklyn (OR 0.98, p=.686) and Staten Island (OR 0.86, p=.164) remain indistinguishable from Manhattan. An earlier 50,000-row sample of this data had shown a much larger, clearly significant gap (Bronx p=.014, Queens p=.009) — that result didn't replicate against the complete population. See Reproduce this for why.

Why might an effect this size exist?

Six mechanisms tested against the complete dataset

Given how small and mostly-non-significant the borough effect above already is, none of this should be read as "explaining a confirmed gap" — it's closer to "does anything make an already-marginal signal look more real." Round 1 (investigate_borough_gap.py) tests three candidate explanations against the complete local extract.

✕ Doesn't help explain it

Is the initial citation itself worse in the Bronx/Queens?

Only slightly. Initial-visit violation counts run a bit higher in the Bronx and Queens (3.39, 3.56) than Manhattan (3.26) — real, but too small a gap to plausibly drive even a 2-point re-grade difference.

✕ Doesn't help explain it

Do Bronx/Queens restaurants have less time to fix the problem?

Ruled out — in the wrong direction, if anything. Bronx and Queens restaurants are re-inspected sooner (median 112–119 days) than Manhattan (135 days), which would predict a worse, not better, outcome under a "less time to fix it" theory.

◐ Real finding, wrong shape

Are they failing to fix the exact same violation?

A recurring violation code strongly predicts a B/C outcome within every borough (roughly 3× higher B/C rate when a code recurs) — a genuinely useful finding about grading generally. But recurrence rates are close enough across boroughs (70–76%, Staten Island the outlier at 63%) that this doesn't explain a borough-specific gap on its own.

◐ Pushes the estimate further down

Does restaurant density explain the gap?

Adding a density proxy (restaurants per community board) attenuates both borough estimates further: Bronx p=.128→.328, Queens p=.041→.099 — Queens moves from just past the significance boundary to clearly not significant. Density is itself correlated with being in Manhattan, so this is ambiguous between "real confound" and "collinearity inflating the uncertainty" — but it doesn't make the effect look more real either way.

? Untestable with this data

Does reporting lag explain the gap?

Not ruled out — genuinely unmeasurable here. The field that looked like a publish date (record_date) is actually a data-download timestamp (3 distinct values across ~295k rows); grade_date equals inspection_date on every graded row.

? Untestable with this data

Does inspector assignment explain the gap?

Still untestable — all 27 fields in the complete extract were enumerated by hand; none identify an inspector, team, or staffing level. DOHMH doesn't publish this.

Every mechanism visible in the public data was tested against the complete dataset. None of them make the Bronx/Queens estimate look more substantial — density pushes Queens from borderline to clearly not significant. The honest read: there isn't a confirmed gap here demanding an explanation, so much as a small, mostly-not-significant signal that nothing available makes look any more real. Full write-up in INVESTIGATION.md.

The data

NYC DOHMH Restaurant Inspection Results

Source: NYC DOHMH Restaurant Inspection Results — the complete table as of a pinned snapshot date (~295,048 rows; see Reproduce this for why it's the whole table rather than a sample). One row = one violation cited on one inspection — not one restaurant, not even one visit. A restaurant cited for six things on one visit produces six rows with the same camis, so any real analysis has to group by restaurant and inspection date first, or it double-counts. See NOTES.md for the full list of data-quality gotchas (borough capitalization silently zeroing out API queries, dba name variants, missing-not-null violation fields).

Modeling choices worth flagging

  • Pre-2023 re-inspections are collapsed into a single "2022 or earlier" category instead of one dummy per year — several individual years (2020: 6 eligible re-inspections, 2021: 2) are still too sparse to estimate stable year-by-year coefficients, even in the complete dataset. Year is a control here, not the variable of interest, so this doesn't affect the borough estimates directly.
  • Cuisine categories with fewer than 20 observations are folded into "Other / rare cuisine" to avoid unstable single-cell estimates.

Limitations

  • The headline result is genuinely weak, not strong: Queens sits right at the edge of conventional significance and Bronx doesn't clear it. Read this as "a small, inconclusive signal," not "confirmed" or "disproven."
  • No multiple-comparisons correction is applied, which makes the above weaker still. Four boroughs are tested against Manhattan simultaneously; at uncorrected α=.05 each, the chance of at least one nominally "significant" result among four is ~18.5% by chance alone, not 5%. A Bonferroni-corrected threshold (α=.0125) isn't cleared by Bronx or Queens.
  • Cross-sectional, not causal: any real (or apparent) borough effect could reflect inspector assignment, restaurant density, reporting lag, or unmeasured neighborhood factors, not something intrinsic to the borough itself.
  • Cuisine folding trades cuisine-level detail for model stability, the same way the year-bucketing does.

Reproduce this

Why the numbers on this page changed

An earlier version of download_data.py pulled 50,000 rows with no date filter and no explicit sort order. That had two problems. First, it wasn't reproducible: Socrata doesn't guarantee stable row ordering for offset-based pagination without an explicit sort, and the feed is live, so re-running that script later silently returned a different slice than whoever ran it before you got — the specific 57%-vs-50%, clearly-significant result quoted in earlier versions of this page can't be regenerated from the documented steps. Second, the obvious fix made things worse: pinning a deterministic sort order requires some sort key, and every one available here introduces real bias for this paired initial→re-inspection design. Ordering by date right-censors the sample — recent initial inspections haven't had time to get re-inspected yet, which collapsed the paired sample from 3,921 to 779 re-inspections in testing and pushed every p-value into insignificance as a pure artifact of losing 80% of the data. Ordering by restaurant ID selected only long-tenured restaurants, since IDs are assigned roughly chronologically.

The fix: download_data.py now pulls the complete table (paginated, ~295k rows) bounded only by a pinned SNAPSHOT_CUTOFF date, with a sort order used purely to make pagination stable, not to select a biased subset. Re-running it returns the same rows every time — verified across three separate pulls. Every number on this page changed from an earlier version because this is what the complete population actually shows, not a different sample.

Requires Python 3 with pandas, numpy, and requests (for the downloader).

pip install -r requirements.txt
python3 data/restaurant-analysis/download_data.py    # first: pulls the complete ~295k-row table (~1 minute)
python3 analyze_reinspection_model.py                # borough-adjusted logistic model (~15s)
python3 investigate_borough_gap.py                   # round 1 of the mechanism hunt (~25s)
python3 investigate_deeper_mechanisms.py             # round 2 of the mechanism hunt (~15s)
python3 check_model_specification.py                 # specification checks, see INVESTIGATION.md (~15s)
python3 -m unittest discover -s tests -v             # run the test suite

All four exit with a clear message (not a traceback) if you skip the first step. None of them print anything while working — if one goes quiet for a while, that's expected, not stuck.
